# Incident Investigation Report — DeepStream Multi-Stream Pipeline (C2 Center)

**Investigation ID:** RCA-2026-05-09-DS001  
**Date:** 2026-05-09  
**Author:** Senior Incident Response Analyst  
**Status:** Resolved (with Performance Caveats)  
**Severity:** P1 — Edge AI Pipeline Total Outage (Initial) / Performance Degradation (Current)  
**Final Outcome:** Pipeline restored to operational state at **~27 FPS** on both video sources, but operating at absolute hardware limits.  

---

## 1. Executive Summary

The C2 Center Edge AI subsystem (NVIDIA Jetson Nano running DeepStream 6.0.1 inside a Docker container) failed to start despite multiple configuration corrections. What was initially diagnosed as a series of unrelated configuration errors was eventually traced to a **cascading failure mode**: an environmental EGL display initialization failure was silently blacklisting **13 critical GStreamer DeepStream plugins**, including `nvstreammux`, `nvinfer`, `nvtracker`, and `nvosd`. 

After the EGL issue was resolved by forcing headless mode, a second-order failure surfaced: the ONNX model was statically exported with `batch=1`, conflicting with the requested `batch-size=2`. This was resolved by forcing sequential inference (`batch-size=1` for `primary-gie` and `streammux`).

While the pipeline is now operational and processing two RTSP streams, **post-incident telemetry (`jtop`) reveals the Jetson Nano is saturated**. The GPU is at 98% utilization, and one CPU core is pegged at 99%. The system is highly vulnerable to thermal throttling, jitter, and frame drops, making the current dual-stream YOLOv8 architecture unstable for long-duration production usage on this specific hardware.

### 5.2 Performance Reality Check (Jetson Nano)

The telemetry proves that the bottleneck is **not RAM** (~1.8GB / 3.9GB used). It is primarily:
1. **GPU saturation**
2. **Decoder/inference pipeline pressure** (NVDEC active at ~716 MHz)
3. **CPU scheduling overhead** (Core #4 pegged)

A Jetson Nano is extremely constrained for modern multi-stream AI. Running decode + inference + tracking + RTSP + YOLOv8 + FP32 on two simultaneous 1080p streams is heavy.
* **Realistic Limits:** 1x 1080p YOLO stream (Stable), 2x 720p optimized streams (Possible), 2x 1080p YOLO streams (Unstable/Jittery).

What this means for the current setup:
* **Frame drops, pipeline latency growth, queue buildup, and RTSP stutter** are highly likely.
* **Thermal throttling risk** is imminent as uptime increases under sustained 8.2W power draw.

## 6. Root Cause Analysis

### 6.1 Primary Root Cause (RC-1): EGL Display Cascade
In a headless SSH session, the EGL context creation fails. The DeepStream plugins' `init()` routines return failure, and GStreamer permanently blacklists them in `~/.cache/gstreamer-1.0/registry.aarch64.bin`. *Resolved by stripping EGL dependencies.*

### 6.2 Secondary Root Cause (RC-2): ONNX Static Batch Dimension
The PyTorch-to-ONNX export omitted `dynamic_axes`. TensorRT honored the fixed shape `[1, 3, 640, 640]`, producing an engine strictly limited to `maxBatchSize=1`. *Mitigated by forcing sequential inference.*

### 6.3 Tertiary Root Cause (RC-3): Compute Saturation
The YOLOv8 architecture (even if FP16, though logs suggest FP32 build attempts occurred) combined with the overhead of multi-stream demuxing, tracking, and unoptimized post-processing threads heavily overwhelms the 128-core Maxwell GPU and Quad-core ARM A57 CPU. The 99% CPU core indicates a single-threaded bottleneck, likely within the NvDsInfer bounding box parsing or message broker serialization.

---

## 7. Mitigation Attempts & Successful Fixes

### 7.1 Successful Fixes (Pipeline Initialization)
* **M-1:** Stripped EGL-coupled sink stubs and forced `EGL_DISPLAY=none` to bypass plugin blacklisting.
* **M-2:** Cleared GStreamer registry cache.
* **M-3:** Aligned `batch-size=1` across `[primary-gie]` and `[streammux]` to match ONNX static dimensions, avoiding TRT rebuild crashes.

## 8. Remaining Risks

| ID | Risk | Impact | Mitigation Path |
|---|---|---|---|
| R-01 | **Hardware Overload:** CPU Core #4 pegged at 99%, GPU at 98%. | Latency accumulation, dropped frames, thermal throttling, pipeline collapse. | Reduce stream resolution to 720p. Optimize YOLO model (pruning, INT8/FP16 strict). Disable tracking if not strictly necessary. |
| R-02 | **Fake Metadata:** `c2_payload.cpp` emits hardcoded `tracking_id=45`. | Semantically meaningless analytics downstream. | Rewrite C++ payload builder to parse actual `NvDsObjectMeta`. |
| R-03 | **ONNX Static Batch=1:** Sequential inference for 2 streams halves theoretical throughput. | Latency spikes when both cameras have busy scenes. | Re-export ONNX with dynamic batch axis. Rebuild TRT engine for `batch-size=2`. |
| R-04 | **Tracker not validated:** Tracker was disabled during isolation testing. | Required for Option D analytics. Adding it will further spike GPU/CPU usage. | Re-enable and monitor `jtop`. If it pushes system over the edge, Nano hardware is insufficient. |

## 9. Recommendations

### 9.1 Immediate 
1. **Acknowledge Hardware Limits:** The system is operating at the absolute ceiling. Expect instability.
2. **Fix `c2_payload.cpp`:** Before testing backend analytics, the payload builder must emit real tracking IDs.
3. **Monitor Thermals:** Run `jtop` continuously during tests to watch for thermal throttling.

### 9.2 Medium-Term (Optimization)
4. **Re-export ONNX:** Export the model with dynamic batching.
5. **Precision Reduction:** Ensure the TensorRT engine is built using FP16 (or INT8 with calibration) rather than FP32.
6. **Resolution Downscaling:** If instability occurs, downscale RTSP inputs to 720p or lower the frame rate before inference.
